# W3 — Интеграция утверждённой карты города

**Проект:** «Мир Раскола: Право на порядок»  
**Редакция спецификации:** 1.0 · 8 ноября 2026 г.  
**Назначение:** готовое производственное задание для ChatGPT Work, строго ограниченное картой и её интерактивностью.  
**Статус:** утверждены исходный арт и общая компоновка главного UI; **геометрия клика, положение маркеров и игровые времена из этого пакета — подготовленные координаты для проверки, не финально утверждённые правила баланса или география лора**.

## 0. Пределы задачи и неизменяемые решения

1. **Не изменять пиксели утверждённого арта** `assets/approved_map_original_1672x941.png`. SHA-256 записан в `data/map_config.json`. Эта карта — *последнее утверждённое изображение* с медицинским комплексом слева сверху, администрацией в центре, научным кварталом справа сверху, промышленностью слева снизу, садами справа и жильём внизу. Старый файл `Mir_Raskola_City_Map_Clean_3840x2160.png` относится к другому варианту и НЕ должен быть использован вместо этой карты.
2. Не менять утверждённую композицию приложения: **верхняя панель времени/ресурсов, список вызовов слева, карта по центру, карточка происшествия справа только при выборе, отряды в нижней полосе, основные разделы в самом низу**. Боковые панели сворачиваются. В режиме наблюдения правая панель закрыта.
3. Карта — **не** территориальная стратегия. Никаких владельцев районов, цветовых заливок захвата, гарнизонов, фронтов, экспансии и условий победы через контроль территории.
4. Нельзя впекать названия, маркеры, линии патрулей и тревоги в изображение. Они живут в отдельных SVG/DOM/canvas-слоях на общей системе координат.
5. В рамках W3 реализуется отображение и связка с существующим UI, **не пересчитывается** баланс боя, найма, вероятностей или сюжет.
6. Слово «район» здесь означает место патрулирования, происшествий и гражданскую статистику, **не собственность игрока**. Клики по полигонам выбирают район; границы полигонов являются условными зонами попадания, а не утверждёнными административными рубежами канона.

## 1. Точный исходный ресурс

| Параметр | Значение |
|---|---|
| Файл | `assets/approved_map_original_1672x941.png` |
| Натуральный размер | **1672 × 941 px** |
| Пропорция | **1672:941 ≈ 1.7768:1** |
| Координаты | `(0,0)` — левый верхний угол оригинала; `(1,1)` — правый нижний |
| Положение данных | `data/map_config.json` — единственный источник координат |
| Изменение арта | **Запрещено** в этом этапе; производные WebP/AVIF разрешены лишь как безвизуальные экспорты для скорости загрузки |
| Физический масштаб города | Не определён; **игровая** длительность поездок задаётся взвешенными рёбрами графа |

Система нормализованных координат:

```text
imageX = normalizedX * 1672
imageY = normalizedY * 941
screenX = viewportLeft + cameraOffsetX + imageX * scale
screenY = viewportTop  + cameraOffsetY + imageY * scale
baseScale = max(viewportWidth/1672, viewportHeight/941)    // COVER
scale = baseScale * zoom
cameraOffsetX = (viewportWidth  - 1672*scale)/2 + panX
cameraOffsetY = (viewportHeight -  941*scale)/2 + panY
1 <= zoom <= 2.5
```

**Нельзя** делать координаты маркеров процентами от CSS-контейнера, а изображение масштабировать независимым `background-size: cover`: при таком подходе метки оторвутся от объектов на планшете. Размер карты, SVG-полигонов, дорог и якорей должен задаваться одной и той же матрицей. Декоративные иконки отображаются в отдельном **экранном** слое фиксированного размера и пересчитывают позиции через `worldToScreen`.

Камера: режим `cover`, без деформации и чёрных полос. После смены панели сохранять zoom и положение; если часть исходной карты стала невидима, ограничить `panX/panY` так, чтобы поле изображения полностью покрывало видимую область. Автоматическое наведение на событие допускается, **только если метка оказалась вне безопасной видимой зоны** (60 px от боков, 70 px сверху, 110 px снизу на desktop-режиме). При необходимости увеличивать zoom, а не оставлять пустую область после смещения.

Смена расположения на новом арте обязательна: координаты из старого `app.js` устарели. Полное определение каждого полигона и 3 точек появления происшествий — в `data/map_config.json`.

| ID | Название | Центр изображения, пикс. | Центр, нормализованный | Игровая роль |
|---|---|---|---|---|

| `industry` | Промышленный сектор | (272, 537) | (0.1627, 0.5707) | фабрики, транспорт производства |
| `gardens` | Северные сады | (1435, 532) | (0.8583, 0.5654) | биокупола, гражданская среда |
| `residential` | Жилые кварталы | (836, 713) | (0.5000, 0.7577) | жильё, гражданские службы |

*Примечание:* таблица даёт округлённые значения для человека; система использует значения `labelAnchor` из JSON с точностью шести десятичных разрядов. Полигон — **hit-zone** (область взаимодействия), не закрашиваемая граница владения. Во время стандартного режима `events` она прозрачна и появляется по hover/selection, а в режиме `districts` может показывать полупрозрачный контур.

Поведение выбора:
- клик/тап по свободному участку полигона выбирает район и открывает его краткую карточку;
- клик по значку события в любом слое — выбирает **событие**, а не район под ним;
- клик по значку отряда — открывает контекст отряда;
- выбор другого района сбрасывает только текущую локальную выборку, но **не** игровые назначения/маршруты;
- на клавиатуре полигоны доступны через Tab/Enter/Space, при наведении названы для скринридера.

## 3. Маркеры происшествий

Данные событий сохраняются в Game Core, но выводятся через карту. Игровое событие обязано содержать `id`, `districtId`, `spawnId`, `severity`, `deadlineMinutes`, `state`. Координату разрешается вычислять **только** по точке `districts[].spawnPoints[]`. Один и тот же `incidentId` в списке вызовов и на карте.

Пять стартовых примеров есть в `data/incidents_demo.json`:

| Event ID | Район | Координата, пикс. | Начальная угроза |
|---|---|---|---|
| `medriot` | medical | (350, 229) | critical |
| `bioleak` | science | (1374, 266) | high |
| `raid` | industry | (307, 553) | high |
| `missing` | admin | (866, 418) | medium |
| `illegal` | residential | (828, 685) | medium |

Состояния **в игровой модели**:

```text
new -> acknowledged -> assigned -> en_route -> on_scene ->
  resolved_success | resolved_partial | failed

new/acknowledged/assigned/en_route -> escalated (не обязательно удаление)
new/acknowledged -> expired (только если тип события действительно имеет deadlineType=expire)
```

`selectedIncidentId` — **отдельное локальное состояние интерфейса**. Выбор в списке и на карте не означает `acknowledged`, если игрок не подтвердил принятие вызова. Не путать UI-выделение и смену игрового статуса.

Визуальные статусы:
- **critical**: красный, восклицательный знак, высокая приоритетность;
- **high**: янтарный/жёлтый, треугольник;
- **medium**: нейтрально-синий, точка/значок типа;
- **en_route**: тонкое кольцо назначения, пунктир к назначенному отряду, таймер прибытия;
- **on_scene**: значок в форме двойной метки/операции, без повторной отправки;
- **resolved**: скрыт с оперативной карты, остаётся в архиве/журнале.

Срок в карточке — «до ухудшения» и после истечения может вызывать эскалацию, а не обязательное мгновенное поражение. Семантика каждого события задаётся Game Core (`deadlineType`), не HUD.

Один маркер — не меньше **44×44 CSS px** и не меньше **8 px** расстояния между неперекрывающимися визуальными областями. При пересечении: приоритет critical > high > medium, смещение **только экранного маркера** с линией к истинной точке; world anchor не меняется. Для 3+ событий в пределах 48 px — кластер с количеством и разворотом по тапу.

Время и маркеры не должны использовать случайные координаты при каждом рендере: spawn выбирается один раз при создании события и затем сохраняется в savegame.

## 4. Отряды, маршруты, движение

Сейчас в старом прототипе у отряда есть `x/y` в процентах карты и условный `duration`; эти поля **нельзя** переносить в новую карту без миграции. Использовать устойчивые `currentNodeId`, `routeEdgeIds`, `edgeProgress`, `destinationIncidentId`, `state`, `etaGameMinutes`.

Канонические состояния отображения:

| Состояние | На карте | Полоса отрядов | Разрешённая команда |
|---|---|---|---|
| `ready` | узел базирования | зелёный | отправка |
| `en_route` | движущийся маркер | синий / ETA | смена приказа только по правилам операции |
| `on_scene` | цель события | жёлтый | операции / помощь |
| `returning` | движущийся маркер | синий / ETA | изменение базы в разрешённых случаях |
| `resting` | только по слою «Патрули» | серый | недоступен |
| `treatment` | клиника/скрыт по настройке | красный | недоступен |
| `recovery` | база/клиника | янтарный | недоступен |
| `unavailable` | скрыт | серый | недоступен |

Миграция существующих статусов: `mission` -> `on_scene` или `en_route` **в зависимости от фактического задания**, `rest` -> `resting`, `healing` -> `treatment`; `recovery` и `ready` сохраняют смысл. Не трактовать автоматически `mission` как боевой контакт без данных операции.

**Транспортная сеть:** файл `data/map_config.json -> roadNetwork` содержит 20 узлов и 24 двусторонних ребра. Каждый узел имеет нормализованную позицию, каждое ребро — список точек `polyline` и `baselineMinutes` в условных игровых минутах. Это **рабочая** визуальная аппроксимация нарисованных магистралей, а не точная трассировка дорожного полотна.

Алгоритм:
1. Проверить готовность и доступность отряда, тип транспорта и условия операции.
2. Выбрать начальный узел текущей позиции (`currentNodeId`) и целевой `serviceNode` района происшествия.
3. Построить кратчайший путь Dijkstra/A* по **весу времени**, не по расстоянию между пикселями. Если дороги закрыты, исключить `enabled=false`.
4. Время ребра: `baseMinutes × trafficFactor × hazardFactor × vehicleFactor`. Коэффициенты пока заглушки `=1`. Модификаторы из будущей игровой модели должны быть ограничены и покрыты отдельным баланс-тестом.
5. Добавить финальный участок `lastMileMinutes` до конкретного `spawnPoint` (стартовое значение **1,5 игровые минуты**; баланс может изменить).
6. Отображать ETA округлённым **вверх** до целой минуты, пересчитывать только при изменении маршрута/состояния дорог/скорости транспорта, не на каждом кадре.
7. Анимация — по совокупной длине сегментов `polyline` в пределах каждого ребра и времени этого ребра. **Общий прогресс** в игровом времени, а не синхронно с wall-clock независимо от pause.
8. Состояние `en_route` -> `on_scene` при нулевом оставшемся времени; списки вызовов и отрядов обновляются синхронно. При `paused=true` положение отряда и ETA не меняются.
9. При блокировке ребра до въезда — строить новый путь, уведомлять игрока об изменённом ETA; если нет пути — показать «Нет доступного маршрута», не телепортировать.

**Пример проверки веса:** `ADMIN_DEPOT` → `ADMIN_W` (3) → `MED_RAMP` (3) → `MED_MAIN` (3) + 1,5 до `medriot` = **10,5**, на карточке показываем **≈11 игровых минут**. Это расчёт игрового графа; он не претендует на физические характеристики города.

**Требование к кадровой системе:** потеря, лечение, отпуск и перевод сотрудников обновляют состав отрядов независимо от карты; карта берёт агрегированное состояние от Game Core. Никакой самостоятельной второй кадровой модели внутри Map.

## 5. Слои и управление

Режимы **одного и того же изображения**, без отдельных карт:

| `layerId` | По умолчанию видно | Включает | Не включает |
|---|---|---|---|
| `events` | да | вызовы, приоритеты, выбранная цель | цветную заливку владения |
| `patrols` | нет | доступные/движущиеся отряды, занятость, по запросу маршрут | чужие военные фронты |
| `risks` | нет | гражданскую опасность и известные угрозы | скрытую игроку информацию |
| `infrastructure` | нет | клиники, базы, транспортные узлы, значимые здания | покупку/захват районов |
| `districts` | нет | названия и краткую статистику шести районов, подсветку выбранного | политическую перекраску |
| `route-preview` | по контексту | текущий рассчитанный маршрут и ETA | все 24 линии одновременно |

Рекомендуемый UX: `events` в наблюдении, справа закрыто. При выборе события открывается правая карточка, где есть назначения и прогнозы. Не показывать одновременно все имена районов, все трассы, все патрули и все события в штатном режиме. В QA-просмотрщике имеется технический режим «Все слои» специально для проверки геометрии, **не** для постоянной игры.

Слои должны поддерживать pointer/touch и клавиатуру. Маркеры всегда выше полигонов. Панель явным крестиком закрывается без сброса `selectedIncidentId`; при повторном выборе события информация восстанавливается. Камера при этом сохраняет выбранное положение, кроме минимального обеспечения видимости выбранной метки.

## 6. Взаимодействия и управление камерой

- Панорамирование: mouse drag / 1 палец (не перехватывать кнопки); desktop wheel zoom относительно курсора; планшет pinch-to-zoom вокруг центра жеста; отдельные кнопки +, −, reset.
- Стартовый масштаб: `zoom=1` относительно `cover`, рабочая область полностью заполнена; в viewport может быть скрыта часть крайних объектов, но все шесть районов доступны через клики/список/автоподвод камеры.
- Zoom в диапазоне 1.0–2.5; любые клики и маршруты сохраняют совпадение независимо от масштаба.
- Маркеры не масштабируются вместе с картой: **постоянные CSS-пиксели** на экранном слое; линии полигонов и дорог масштабируются с изображением.
- Открытие/закрытие боковой панели **не** возвращает zoom=1; если цель становится невидимой, camera ensure-visible без скачка в пустое пространство.
- В режиме 11″ горизонтального планшета — кнопки от 44×44 CSS px, базовый читаемый шрифт не меньше 14 CSS px для вторичного текста, 16 px для основной интерактивной информации.
- При ширине <950 CSS px левая/правая панели должны становиться **накладными drawer**, а не постоянно сужать карту до полосы; можно закрыть тапом вне панели/Escape, подтверждение операций не теряется. В текущем QA-просмотрщике этот мобильный UX **не реализован полностью**, это обязательное требование для Work.
- `prefers-reduced-motion`: движение патруля показывать обновлением положения без непрерывной анимации, сохранить достоверность времени прибытия.
- Offline: отсутствие сети не должно мешать загрузке утверждённого PNG и локальных данных.

## 7. Состояния, события, сохранения

Три уровня хранения:

**Game Core:** события, назначенные отряды, игровые минуты, маршрут/текущее ребро, статус подразделения, флаги дорог, состояние досье. Это сериализуемая детерминированная логика.

**Map View:** `selectedDistrictId`, `selectedIncidentId`, `activeLayerId`, `cameraZoom`, `cameraPan`, `leftPanelOpen`, `rightPanelOpen`, `mapAssetId`. Сохранение UI отдельно от Game Core допустимо.

**Art Assets:** только идентификатор и путь к утверждённому изображению, 6 полигонов, точки и граф. Не сериализовать пиксели картинки внутрь каждой сохранённой партии.

Пример модуля событий:

```text
INCIDENT_CREATED(id, districtId, spawnId)
INCIDENT_SELECTED(id)           // только интерфейс
INCIDENT_ACKNOWLEDGED(id)       // игровое действие, если нужно
SQUAD_DISPATCHED(squadId, incidentId, route)
SQUAD_ROUTE_CHANGED(squadId, remainingRoute, eta)
SQUAD_ARRIVED(squadId, incidentId)
INCIDENT_ESCALATED(id)
INCIDENT_RESOLVED(id, result)
MAP_LAYER_CHANGED(layerId)
MAP_CAMERA_CHANGED(zoom, pan)
```

Не использовать `setInterval` как источник истины времени и не привязывать прогресс движения к частоте кадров. Источник времени — Game Core; визуальный цикл только интерполирует два валидных состояния. При сохранении/загрузке маршрут и ETA должны воспроизводиться, без удвоения таймера и без телепортации.

## 8. Производительность и качество

- Desktop 1600×900, планшет 1194×834, телефон горизонтальный 844×390 — обязательные размеры проверок; 844×390 требует отдельного drawer-UX.
- Изображение PNG нативного размера сохраняется в репозитории; для production допустим WebP/AVIF с различными профилями качества и fallback без видимого изменения композиции.
- **Целевые пороги** (не выданы за уже достигнутые): отклик клика/тапа <100 мс на целевом устройстве; интерфейс устойчиво ≥30 fps при 6 патрулях и 20 событиях на горизонтальном планшете; без ошибок console; без layout overflow; обновление списка и карты в одном игровом тике.
- Перерисовывать SVG-слои только при изменении данных/камеры, не пересоздавать всю разметку при каждом кадре.
- У каждого интерактивного элемента есть semantic name, клавиатурная активация и контрастный focus-visible.

## 9. Критерий готовности W3

W3 считается готовым **только если**: последняя утверждённая карта внедрена в существующий интерфейс, работают 6 районов, события и синхронный список вызовов, минимум два маршрута со временем в пути, движение пауза/скорости, корректное переключение слоёв, камера не ломается от открытия панелей, есть сохранение и загрузка, нет ошибок тестов и приложены скриншоты состояний на 1600×900 и 1194×834. Для 844×390 требуется адаптированный drawer-режим и скриншот без перекрытых основных кнопок. Валидация в отдельном QA-просмотрщике не заменяет проверку исходного приложения.

**Обязательная граница:** не менять утверждённый арт и дизайн всей остальной игры, пока пользователь не утвердит результат интеграции W3.
